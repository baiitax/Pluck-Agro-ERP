# Database schema (Phases 0–1)

All changes are versioned SQL in `supabase/migrations/` and must be applied in filename order.
Applied migrations are never edited — corrections are new migrations.

## 2. Relationships

```text
auth.users 1─1 profiles 1─0..1 employees *─1 departments
                  │
                  ├─* user_roles *─1 roles *─* permissions   (via role_permissions)
                  ├─* approval_limits        (user OR role, never both)
                  └─* audit_logs             (actor, nullable for system events)

departments 1─< departments            (hierarchy, cycle-guarded)
departments ─< employees
employees   1─< employee_positions
employees   1─< employee_department_history   (one open interval per employee)
employees   1─< employee_emergency_contacts
employees   1─< approval_authorities   (employee XOR role)
employees   1─< approval_delegations   (delegator → delegate, acyclic)
employees   1─< sod_overrides *─1 segregation_of_duties_rules
profiles    1─< account_activity
profiles/employees ─< access_review_records (unique per period + user)
```

## 3. Design rules applied

- UUID primary keys (`gen_random_uuid()`; no extension required on PostgreSQL 13+).
- Explicit foreign keys with deliberate `on delete` behaviour (`restrict` for reference data,
  `cascade` for pure join/identity rows, `set null` for historical actor references).
- `numeric` precision reserved for money/quantity in later phases — **no floats**.
- `timestamptz` for event timestamps, `date` for business dates.
- Check constraints encode hard invariants (employment status enum, permission code format,
  one approval-limit holder, expiry after assignment, code = module‖'.'‖action).
- Unique indexes: employee number, employee email (case-insensitive, non-null),
  department code/name, role code/name, permission code, `(role_id, permission_id)`,
  `(user_id, role_id) where is_active`, one profile per employee.
- Indexes on all foreign keys and on frequently filtered/sorted columns (`created_at desc`,
  employment status, audit module/entity).
- `updated_at` maintained by trigger, not by the application.

## 4. Security functions

| Function | Purpose |
|---|---|
| `private.current_profile_id()` | `auth.uid()` only when the profile is active |
| `private.is_active_profile()` | Boolean gate used by policies |
| `private.has_permission(code)` | Role → permission resolution honouring `is_active` and `expires_at` |
| `private.has_role(code)` | Role membership check |
| `private.current_user_permissions()` | Effective permission array (debug/introspection) |
| `private.guard_profile_privileged_columns()` | Non-admins cannot change `is_active`/`employee_id` on their own profile |
| `private.block_audit_mutation()` | Audit rows cannot be updated or deleted |
| `private.block_self_role_assignment()` | A user can never assign themselves a role |

All `SECURITY DEFINER` functions set `search_path = public, pg_temp`, are read-only where
possible, and have `EXECUTE` revoked from `PUBLIC` and granted narrowly.

## 5. RLS summary

| Table | Read | Write |
|---|---|---|
| `departments` | Any active profile | `departments.manage` |
| `employees` | `employees.view`, else own linked row only | `employees.create` / `employees.update` (never delete) |
| `profiles` | Self, `users.view`, `employees.view` | Self (guarded columns), `users.manage` |
| `roles` / `permissions` / `role_permissions` | Any active profile (catalogue transparency) | `roles.manage` |
| `user_roles` | Self or `users.manage` | `users.manage` **and** not self (policy + trigger) |
| `approval_limits` | Self or `users.manage` | `users.manage` |
| `audit_logs` | `audit.view` | **No grants** — trusted server path only |
| `system_settings` | `settings.view` and not `is_sensitive` | `settings.manage` |

`anon` has no grants on application tables; unauthenticated requests are denied by privilege
and policy.

## 6. Verification

`npm run test:db` applies every migration to a real PostgreSQL engine (PGlite) with a
Supabase-compatible `auth` stub, then asserts table creation, RLS enablement, FK presence,
constraint behaviour, seed idempotency, append-only audit, and 19 RLS/privilege scenarios.
